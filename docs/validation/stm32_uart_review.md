# 已烧录 STM32 固件与上位机核对

最新 `te (3).zip` 和 2026-11-01 实机使能超时的检查见 [本次排查记录](uart_enable_20261101.md)。下文保留此前 `te (2)` 的核对历史，ID 和失能查询实现应以实际固件为准。

本文依据用户提供的 `te (2).zip` 源码整理。源码路径为 `Core/Src`、`Core/Inc`；上位机入口为 `src/rebotarm_uart/rebotarm_uart`。

## 已确认的线格式

- UART7：115200、8N1。
- 主机到 STM32：72 字节，`AA + 7×(int16 q, int16 v, uint16 Kp, uint16 Kd, int16 tau) + 55`。
- STM32 到主机：131 字节，`BB + 7×18 字节反馈块 + 3 个组标志 + 44`。
- 当前固件块顺序固定为 J4310×2、J4340P×3、Motorevo×2；上位机用
  `slot_joint_ids=[4,6,1,2,3,5,7]` 映射到逻辑关节。
- 反馈块中的本地 Motor ID 为 `[1, 2, 8, 9, 0x10, 1, 2]`。它不是逻辑关节号；CAN Master ID `[4,5,0x11,0x12,0x13,6,7]` 不在线路中传输。

### 实体电机与线槽位

已确认实体顺序为：J1～J3 = DM4340P，J4/J6 = DM4310，J5/J7 = PA43。
固定帧没有轴 ID，因此上位机必须保持线槽位顺序 `[J4,J6,J1,J2,J3,J5,J7]`；反馈也必须按同一映射还原。该映射已写入统一硬件配置并由 UART 编解码器使用。

## 位置和速度含义

`q` 是相对 MCU 启动零点的绝对位置，不能累加。固件在每次启动时把当前电机位置设置为零，所以这个零点尚未和 URDF 或真机机械零点对齐。

`v` 是位置轨迹限速，不是独立的速度闭环目标。固件约每 5 ms 以该限速推进内部轨迹；`v=0` 会暂停位置轨迹。上位机现在把 `JointPosVelCmd.vlim` 传入该字段，并按每轴固件上限裁减。上位机仍应以明显高于 500 ms 的频率发送完整帧。

## 安全参数

下表按 STM32 线槽位分组；上位机已映射回逻辑关节后再应用这些限值。

| 组 | 速度限值 | 前馈力矩限值 | 默认 Kp/Kd |
|---|---:|---:|---|
| J4310×2 | 0.3 rad/s | 10 Nm | 1.2 / 0.6 |
| J4340P×3 | 0.3 rad/s | 1 Nm | 3.1 / 1.4 |
| Motorevo×2 | 0.5 rad/s | 3 Nm | 0.3 / 0.3 |

线格式的 Kp 上限为 65.535，Kd 上限为 5。这里的力矩限值是固件接收和 CAN 映射限值，不等于机械臂关节已经完成的负载标定。

## 状态和生命周期

- 有效 72 字节命令会自动进入使能流程；没有独立 enable/disable 帧。
- 命令看门狗为 500 ms，反馈新鲜度和使能确认约为 100 ms，反馈周期约 20 ms。
- 上位机的 `/enable` 首次发包允许 CAN 反馈过期，先发零限速、零增益、零前馈帧；收到七轴新鲜运行反馈后接入正常目标，并检查起始偏差。`/disable` 停止发送，实际停机由 MCU 看门狗完成。
- Motorevo 状态字的 bit0 是使能位，`status & 0xfffe` 是故障位。之前将高位状态字当成正常值的测试已修正。
- 固件没有 CRC、序号或时间戳；上位机只能校验固定长度、帧头尾、ID、状态和浮点有限性。

## 尚未完成的真机条件

1. 将启动零点与 URDF/机械零点建立标定流程，并确认关节方向和限位。
2. 用示波器或串口抓包确认实际反馈 ID、CAN Master 配置和看门狗停机动作。
3. 逐关节低增益、低速、限力矩验证；确认 J4340P 的 CAN `V_MAX/T_MAX` 与实际电机配置一致。
4. 当前固件仍在下位机做 5 ms 插值；若要求“轨迹插值全部在上位机、STM32 只执行”，必须修改固件并重新烧录，不能仅修改 Python。

重力前馈只有在 UART 启动零点已经映射到 URDF 零点后才能开启。上位机现在使用 `uart.gravity` 中的偏置、方向和缩放计算 `g(q)`，并按每轴 UART 力矩上限限幅；默认关闭。

上位机没有打开真实串口或发送电机命令；本次验证使用协议单元测试、PTY 对端和固件提供的原生回归 harness。

附件原生 harness 的 `invalid_gains` 场景仍把 Motorevo 默认 Kp 按旧的 `0.2` 计算（期望 CAN 编码 1）；当前已烧录头文件明确是 `MOTOR2_APP_DEFAULT_KP=0.3`，对应编码 2。因此该场景会失败，属于测试期望未同步，不能据此修改上位机协议。

## `feedback_fresh` 七轴全为 0：失能时缺少反馈查询

2026-10-23 重新核对了压缩包原文件；用于分析的六个电机驱动/应用 C 文件、`fdcan.c` 和 `main.c` 与 `te (2).zip` 内文件逐字节一致。

### 已确认的代码路径

1. `motor_app.c:281`、`motor3_app.c:210`、`motor2_app.c:215` 都按下面的条件填写每个 18 字节块的偏移 2：

   ```c
   fresh = (rx_count != 0) && ((uint32_t)(HAL_GetTick() - last_rx_ms) < 100);
   ```

2. `rx_count` 和 `last_rx_ms` 只在 CAN 报文通过 `DMJ4310_OnRx()` / `Motorevo_OnRx()` 校验后更新。`GetFeedback()` 只复制缓存，UART 每 20 ms 发一次缓存不会刷新这些值。
3. 三组 `IDLE` 分支都在没有有效 UART 命令时返回，不发送周期查询。PA43 的 `Motorevo_RequestFeedback()` 虽已实现，但应用层没有调用。
4. 修复前，上位机 `link.py` 在七轴 CAN 反馈全部新鲜之前拒绝开始发送；`bridge.py` 在任一轴过期时也不发布新的 `joint_states`，因此依赖实测位置的保持目标发布器同样会等待。

修复前，如果电机采用请求后应答、或失能后停止主动上报的工作方式，就形成：

```text
没有新鲜反馈 → 上位机不发 72 字节
            → STM32 保持 IDLE，也不查询
            → 电机没有新的应答 → 反馈持续过期
```

这能解释“串口助手发 72 字节能转，而 ROS enable 被拦截”：串口助手直接触发下位机使能流程；该流程允许从没有新鲜反馈的 IDLE 状态发送 CAN 使能，再等待使能后的新反馈。上位机增加的前置条件与这个启动流程不匹配。仅凭失能时 `fresh=0`，不能断言 CAN 接线或接收功能损坏。

### 离线复现与结论边界

使用附件原生 HAL 模拟环境运行原 C 源码，并用本项目 Python 解码器解析其实际生成的 131 字节：

| 模拟阶段 | 本阶段累计 CAN 发送数（初始化后计） | 七轴 fresh | 三组 flags |
|---|---:|---|---|
| 注入一次失能反馈后 20 ms，未下发目标 | 0 | `1111111` | `0,0,0` |
| 同一次反馈后 120 ms，未下发目标 | 0 | `0000000` | `0,0,0` |
| 注入有效 72 字节，再模拟电机正常应答 | 21 | `1111111` | `3,3,3` |

这确认了空闲查询缺失和启动条件冲突，也确认了 `fresh` 的 C 打包与 Python 读取偏移一致。电机应答由模拟环境注入；尚不能据此证明实物一定采用请求应答方式，也不能排除反馈 ID 或 CAN 帧格式不匹配。

要区分两类原因，查看已有控制期间的抓包或 STM32 调试器：若发送命令期间七轴 `rx_count` 持续增长，停发后不再增长，则应先修复失能查询；若控制期间仍不增长，则检查 CAN 接收过滤器、反馈 ID、帧类型和接收中断。131 字节 UART 包本身没有携带 `rx_count`，仅有 `fresh` 无法区分“从未收到”和“曾收到但已过期”。

### 上位机已按新的启动要求修复

用户要求首次发送不检查 CAN 新鲜度、使能后再检查。目前 `link.py` 已采用如下流程：

1. 首次发送不检查启动前的 UART/CAN 状态、初始化标志或旧使能位，直接发送零输出握手帧；
2. 使能等待阶段按周期发送位置/限速/Kp/Kd/前馈全零的七轴帧，不依赖上游目标。固件限速为 0 会冻结位置轨迹，零增益不会按零位置施加位置控制力矩。
3. 只有本次已经发包，且七轴反馈全部新鲜、七轴使能、三组运行和命令新鲜时，才确认使能；等待期间的过期反馈不会立即中断，默认 2 秒超时则停发。
4. 新测量到达后检查正常目标起始偏差；若上游仍在等待测量，短暂使用新实测位置的零输出目标，受同一 120 ms 上游超时限制。
5. 正常运行后继续严格检查各轴 CAN 新鲜度、UART 超时、上游超时及故障。`bridge.py` 继续只发布新鲜测量。

协议与 PTY 回归覆盖失能缓存全过期后启动、延迟应答、没有上游目标时启动、缺轴应答超时、起始目标偏差和运行后反馈掉线。验证不连接真机，也不发送真实电机命令。

### 下位机可进一步改进的查询

- 在下位机加入独立的失能状态查询，周期明显小于 100 ms（例如每轴 20～50 ms），不依赖收到运动目标；保持主机对实测位置和运行反馈的检查。
- PA43 可使用现有 `Motorevo_RequestFeedback()`，对应 `0x100 + Motor ID` 的 `FF FF FF FF FF FF FF FA`；手册要求电机固件支持该查询（260617 以后）。
- 达妙需要确认实际型号/固件支持的状态查询或失能主动上报方式；不能直接套用 PA43 的 `FA`，也不能把寄存器读取应答当作普通 MIT 状态帧解析。
- 查询任务不能刷新运动命令看门狗、不能调用使能，也不能把 `fresh` 固定成 1。没有新反馈时仍应如实报告过期。

另有独立风险：J3 的 Motor ID 为 `0x10`，手册的反馈首字节为 `ID | (ERR << 4)`，而驱动按 `d[0] >> 4` 取状态。如果实物将完整 `0x10` 写入该字节，失能状态也可能被解释成 1。需要核对原始 CAN 首字节；这不影响 `fresh` 的时间计算，也不能解释七轴全为 0。

后续用户确认全部红灯，但主机收到 J3 新鲜状态 1、三组 flags 全 0。手册第 7 页明确 ID 取 CAN_ID 低 8 位；`0x10 | (0 << 4)` 与 `0x10 | (1 << 4)` 相同，符合该状态歧义。推荐把 J3 控制 ID 改为 `0x0A`，同步修改电机、下位机和上位机；[补丁与验证步骤](j3_can_id_migration_zh.md) 已备好，当前配置尚未切换，实板待验证。
