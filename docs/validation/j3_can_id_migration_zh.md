# J3 红灯却报告使能：CAN ID 与状态位重叠

> 当前 `te (3)` 源码使用的是电机 ID `0x14`、反馈/Master ID `0x13`；本文下面
> 的 `0x10/0x0A` 表格记录的是旧版本问题，不能替代当前源码配置。

## 现象与原因

已观察到主机报错：`enabled logical joints=[3], group_flags=[0, 0, 0]`；用户确认七轴均为红灯，电机 ID 按十六进制设置。`te (2)` 的 J3 控制 ID 是 `0x10`，反馈/Master ID 是 `0x13`。

DM4340P 手册第 7 页定义 `D[0] = ID | (ERR << 4)`，ID 取 CAN_ID 低 8 位；第 4 页说明红灯常亮对应失能。下位机 `Core/Src/motor.c` 用 `d[0] >> 4` 提取状态，因此：

| J3 控制 ID | 失能 ERR=0 | 使能 ERR=1 | 下位机能否区分 |
|---|---|---|---|
| `0x10`（十进制 16） | `0x10` | `0x10` | 不能，均解析为状态 1 |
| `0x0A`（十进制 10） | `0x0A` | `0x1A` | 能，分别解析为状态 0 和 1 |

上位机接收的是 STM32 已解析的状态，无法从同一个 `0x10` 恢复出真实的使能位。清除该位或强行按组 flags 判定失能也会丢失真实状态。

此前偶尔能 enable，是因为过期 CAN 状态不阻止首发；现在首发流程统一不读取启动前状态，直接发零输出握手帧，再用握手后的新鲜反馈确认运行。J3 状态 1 仍会在握手反馈中作为实际状态处理。

## 修复步骤

本目录的两份补丁已经准备好，**尚未应用到当前配置或下位机工程**。必须同步更新以下三处：

1. 支撑好机械臂，停止控制程序。在达妙调试工具中把 **J3 控制 CAN ID 从 `0x10` 改为 `0x0A`**；若工具显示十进制，则是 **16 改为 10**。保存后按工具要求重启该电机。反馈/Master ID 保持 `0x13`。
2. 修改下位机 `Core/Inc/motor3_app.h`，将 `MOTOR3_APP_ID3` 从 `0x10u` 改为 `0x0Au`，重新编译并烧录。可使用 [STM32 补丁](patches/j3_stm32_id_0a.patch)，以 `te` 工程根目录为补丁根目录。
3. 在上位机工作空间根目录应用 [上位机补丁](patches/j3_host_id_0a.patch)，再同步派生参数：

   ```bash
   patch -p1 < docs/validation/patches/j3_host_id_0a.patch
   python3 scripts/sync_robot_parameters.py
   ```

   补丁只修改唯一硬件参数源中的 J3 `motor_id` 和 UART 第五槽的 `feedback_motor_ids`；同步脚本更新派生 YAML。

三个层级一致后再重启 UART 程序并使能。只修改上位机 YAML 不能改变电机或 STM32 使用的 ID。

## 更新后核对

- J3 仍是第 3 轴的 DM4340P；UART 仍使用第 5 槽，CAN 反馈 ID 仍为 `0x13`。
- UART `feedback_motor_ids` 应为 `[1, 2, 8, 9, 10, 1, 2]`，其中 `10` 是十进制。
- 新鲜反馈下，J3 失能应报告状态 0，使能后应报告状态 1。过期缓存不用于判定当前状态。
- 使能成功仍要求本次发包后的七轴新鲜运行反馈和三组运行/命令新鲜标志齐全。

已验证：两份补丁可以分别应用于当前 `te (2)` 副本和上位机参数源，更新后的逻辑关节/槽位排列及增益保持一致。实物 ID 设置、固件编译烧录和 CAN 原始反馈需在设备侧完成验证。
