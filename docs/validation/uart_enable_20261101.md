# 2026-11-01 UART 使能失败排查

## 结论

本次直接失败原因为 `enable feedback timeout`：主机开始发送握手帧后，未收到七轴同时满足“新鲜反馈、已使能、三组运行”的报告。断电前最后一次完整采样中，J1、J5、夹爪反馈新鲜，**J2、J3、J4、J6 未更新**。

已经排除“电脑完全收不到串口数据”和“上位机因 ID 解码错误丢弃所有报告”。仍需用下位机接收计数或原始 CAN 报文，区分实际反馈 ID/帧格式不符、CAN 通信问题，以及下位机是否收到主机命令；仅凭 UART 报告无法确定其中哪一项。

## 断电前的证据

- 运行后端为 `grasp.launch.py backend:=uart port:=/dev/ttyACM0 start_camera:=false gravity_feedforward:=false`。
- 主机实际收包计数持续增长，曾达到 `rx_frames=13456`，`bad_frames=0`，反馈年龄约 13 ms。
- 本次使能期间主机写出 `tx_frames=99`，约两秒后锁存 `enable feedback timeout`。写出成功只证明本机串口写操作完成，不能代替 STM32 收包确认。
- 曾收到 `group_flags=[0,28,0]`，后来为 `[0,0,0]`；这些是不同时间的报告，不能拼成同一瞬间的状态。
- 早先采样只有 J1 新鲜，最后一次完整采样增加了 J5 和夹爪。断电后 UART 断开是后续事件，不是此前使能超时的原因。

`feedback_motor_ids=[1,2,8,9,20,1,2]` 与当前上位机配置一致。但下位机在组装 UART 报告时，ID 字段取自软件对象配置，**并非直接复制电机收到的 CAN 帧 ID**；因此这组数字不能证明电机内部 ID 已设置正确。反馈位置为零也不能证明该轴在线。

## 下位机代码路径

依据 `/home/wq/下载/te (3).zip` 的 `te/Core` 原始源码：

1. `Src/motor.c:130` 的 `DMJ4310_OnRx()` 只接受正确总线、标准数据帧、指定 Master ID、8 字节长度，以及正确的电机 ID 低四位。通过后才更新 `rx_count` 和 `last_rx_ms`。
2. `Src/motor_app.c:288`、`motor3_app.c:217`、`motor2_app.c:222` 用实际 CAN 接收时间填写 `feedback_fresh`，UART 持续发缓存不会使它变新鲜。
3. `Inc/motor_app.h:21` 和 `motor3_app.h:24` 的使能等待均为 100 ms；必须收到使能后的新反馈，状态为 1，才进入运行。
4. `Src/motor_app.c:173` 在 DM4310 组使能超时后调用 `MotorApp_AbortSharedBus()`；它还会停止同在 FDCAN1 的 DM4340P 组。
5. `group_flags[1]=28` 即 `7<<2`，对应 `MOTOR3_STOP_SHARED_BUS`。它记录上次停机原因，不能单凭此值判断当前仍有总线故障，也不能证明是哪个电机先出问题。

当前需要重点核对的电机如下，ID 均按十六进制写：

| 逻辑关节 | 型号 | 总线 | 控制 ID | 反馈 CAN ID / Master ID | 反馈 Byte0 低四位 |
|---|---|---|---|---|---|
| J2 | DM4340P | FDCAN1 | 0x09 | 0x12 | 0x9 |
| J3 | DM4340P | FDCAN1 | 0x14 | 0x13 | 0x4 |
| J4 | DM4310 | FDCAN1 | 0x01 | 0x04 | 0x1 |
| J6 | DM4310 | FDCAN1 | 0x02 | 0x05 | 0x2 |

这些值是当前固件要求，不代表已实测电机参数。J3 的 0x14 还需核对实际 Byte0 的状态编码，但它不能解释另外三轴缺反馈，不应仅改主机 ID 试错。

## 离线复现

将上位机 `protocol.pack_command()` 生成的真实 72 字节零输出帧，输入附件原 C 源码；使用附件 HAL 模拟环境编译运行，没有访问串口或控制实物。

| 模拟条件 | 三组命令接受计数 | 三组运行标志 | 结果 |
|---|---|---|---|
| 七轴均返回新鲜使能反馈 | 1,1,1 | 3,3,3 | 握手成功，无总线取消 |
| 只有 J1、J5、夹爪应答 | 1,1,1 | 达妙两组未进入运行 | 100 ms 后共享 FDCAN1 停机，DM4340P 停机原因为 7 |

这说明零输出帧的字段、长度、槽位及参数范围与附件源码兼容；模拟不能证明实机收到该帧，也不能替代 CAN 抓包。

## 下一次定位需要的最少信息

在下位机调试器中检查：

- `g_motor_app_diag.accepted_frames/rejected_frames`：区分“STM32 收到并接受主机命令”和“主机仅写出串口”。
- `g_dm4310[0/1].feedback.rx_count`：分别对应 J4/J6。
- `g_dm4340p[0/1/2].feedback.rx_count`：分别对应 J1/J2/J3。

若缺反馈轴计数不增长，记录 FDCAN1 原始接收的 `Identifier`、帧类型、长度和 8 字节载荷，与上表和解析条件对照。过滤器可能先丢弃错误 Master ID，因此最好同时用 CAN 分析仪或电机调试工具读取实际配置。

主机现已把故障瞬间的 `stale_logical_joints`、`enabled_logical_joints`、`group_flags` 和收发计数锁存在 `fault_detail` 中。后续断电仅增加 `transport_error_after_fault`，不覆盖最初故障。使能超时的服务返回也直接列出缺失轴。修改需重启 UART 后端后生效；本次没有重启、使能或发送实物命令。

验证：UART 链路与协议测试共 62 项通过，包含缺轴使能超时、后续断线保留原故障、零输出握手和超时停止发包。

## WCH 厂商驱动恢复后的复查

`/dev/ttyCH343USB0` 已存在、具有读写权限，USB 两个接口均绑定 `usb_ch343`。
本次日志和锁存的故障快照为：

```text
enable feedback timeout
stale logical joints=[2, 3, 4, 6]
enabled logical joints=[1, 5, 7]
group_flags=[1, 29, 3]
tx_frames=100
feedback_age_sec=0.011131141
bad_frames=0
```

这次三组 flags 的 bit0 均为 1，已经确认 STM32 接受了上位机命令；J1、J5、夹爪也报告使能。
因此，上述旧记录中“还需区分 STM32 是否收到命令”的不确定性，本次已排除。
缺失的仍是 J2、J3、J4、J6 的新鲜 CAN 反馈。29 的低两位为 1，高位 28 仍表示
DM4340P 组记录了共享总线停机。

逐项解析 `te (3).zip` 的三个 `motor*_app.h` 并与当前 YAML 比较，七轴的控制 ID
和 Master ID 全部一致。FDCAN1 的三个双 ID 过滤器分别接受 `[0x04,0x05]`、
`[0x11,0x12]` 和 `[0x13,0x13]`；接收回调会遍历两台 DM4310 和三台 DM4340P，
没有发现仅遍历第一台的遗漏。

`Src/motor.c:189` 的 `DMJ4310_Init()` 仅执行 `memset` 和本地对象字段赋值，
没有发送电机 ID、Master ID、控制模式的配置指令。因此附件中的配置与 YAML 一致，
不能进一步证明电机内部保存的配置相同。

当前已定位到 CAN 反馈未被成功接收/解析，但尚不能从 131 字节报告区分“没有原始回包”
与“原始回包被硬件过滤器或软件检查拒绝”。继续定位需读取前述 `rx_count` 和原始
CAN 报文；当前固定 UART 协议没有传输这些信息。此次复查未改 ID、放宽反馈检查、
调用使能或发送电机命令。

## 按新要求调整 enable 服务返回时机

此前首帧已直接发送，但 enable 服务仍阻塞等待运行确认，缺少四轴反馈时返回失败。
现改为服务内直接写入零输出首帧，写入成功立即返回 `success=True`，不以反馈判断
本次服务是否成功。删去了用于阻塞服务的 Event 和结果等待逻辑。

服务返回后，后台继续发送零输出帧并检查真实运行反馈；状态中的
`command_stream_active=true` 表示发包中，`enabled=true` 表示七轴运行已确认。
后台确认默认在 2 秒后超时，报告 `post-enable feedback timeout` 并停止发送。
`te (3)` 自身的 100 ms 使能反馈保护保持原样，因此服务返回成功不能证明四轴缺反馈
已经修复，也不能保证机械臂能够执行轨迹。

验证：66 项链路/协议测试通过；独立 ROS_DOMAIN_ID 下另有 2 项 ROS 集成测试通过，
覆盖无反馈时服务立即确认首帧发送、后台超时停发，以及完整规划/轨迹执行与上游掉线保护。
测试只使用 PTY 假 STM32，没有发送实物命令。运行中的旧后端需要重启才会加载修改。
